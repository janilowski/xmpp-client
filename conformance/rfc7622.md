# RFC 7622: JID preparation and validation

Scope: the client/library JID boundary, including all six address features in
[RFC 7622 §8](https://www.rfc-editor.org/rfc/rfc7622.html#section-8).
This is not server certification or a claim of complete XMPP Core compliance.

## Sources and profile

- RFC 7622 §§3–4 and §7; verified errata 4534 (domain mapping reference) and
  4560 (leading/trailing resource spaces are allowed).
- [RFC 8264](https://www.rfc-editor.org/rfc/rfc8264.html) and
  [RFC 8265](https://www.rfc-editor.org/rfc/rfc8265.html) replace RFC 7564/7613:
  IdentifierClass/UsernameCaseMapped and FreeformClass/OpaqueString.
- IDNA2008: RFC 5890–5893; RFC 5895 mapping. No transitional UTS #46 mapping.
- [RFC 9844 §3](https://www.rfc-editor.org/rfc/rfc9844.html#section-3) removes
  RFC 6874 zone identifiers from this wire grammar. IP literals follow RFC 3986.
- Unicode 16.0.0 repertoire and properties. Native normalization/case conversion
  requires Unicode 16 or later; unassigned input is rejected before mapping so
  a newer runtime cannot silently broaden the selected repertoire.
  A capability guard rejects non-ASCII preparation on older engines instead of
  silently producing partially prepared identities; ASCII remains usable.

## Requirement map

The [standard suite](rfc7622.test.js) is the entry point for pure address behavior.
Each row implements the client's SHOULD as well as the underlying preparation
rules. Optional additional server restrictions are not imposed by the client.

| Feature / clause                 | Executable scenarios                                                                                                                                                                                                    |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Structure, §§3.1–3.2             | Split `/` before `@` and before normalization; domain-only, bare/full, embedded resource separators; reject explicit empty parts; atomic setters                                                                        |
| `address-domain-length`, §3.2    | Empty domain; DNS label 63/64 and domain 253/254 byte boundaries; prepared JID part length check                                                                                                                        |
| `address-domain-prep`, §3.2      | U/A-label equivalence, lowercase, width, NFC, trailing dot, IP literals; fake A-labels, hyphens, initial marks, disallowed/unassigned points, contexts and whole-domain bidi                                            |
| `address-localpart-length`, §3.3 | 1023/1024 UTF-8 bytes, multibyte input and shortening through NFC                                                                                                                                                       |
| `address-localpart-prep`, §3.3   | Width, lowercase (not casefold), NFC, prohibited characters, repertoire, all contextual rule families, bidi and stable output; XEP-0106 remains separate                                                                |
| `address-resource-length`, §3.4  | Empty explicit resource, ASCII and supplementary-plane UTF-8 boundaries                                                                                                                                                 |
| `address-resource-prep`, §3.4    | NFC and non-ASCII spaces; retain case, width, compatibility characters, mixed directionality and edge spaces; reject controls, invalid contexts, private/unassigned points and surrogates                               |
| Examples and identity, §§3.5–4   | Literal examples, canonical equality and deliberately distinct identities; prepare before comparing or emitting addresses                                                                                               |
| Integration, §4                  | [Wire test](rfc7622-wire.test.ts): stream domain, stanza destination, malformed/forged and canonically equivalent IQ sender; [integration tests](../src/jid/test/integration.test.js): resource binding and batch sends |
| Security, §7                     | Invalid characters, lengths, bidi and contextual controls; sender correlation, normalization collisions versus distinct identities; [Chromium bundle test](../browser.test.js)                                          |

[Exhaustive tests](../src/jid/test/unicode.test.js) compare all 1,114,112 code
points against independent classification digests and both profiles' complete
single-code-point results. Multi-character ordering/context cases use literal
vectors, not generated production expectations. Five [mutations](mutations.ts)
remove NFC, byte limits, contexts, bidi and IDNA restrictions; assertions must
detect each one. An additional mutation drops decoded Unicode ranges.
All 20 property repertoires also retain a pre-refactor golden digest, checked
across every code point in Bun and a minified table bundle in Chromium. Decoder
tests cover gaps, range lengths, Unicode endpoints and corrupt encodings.
This is strong bounded evidence, not exhaustive enumeration of
all possible strings or proof of every inherited standard.

## Compatibility and security boundaries

- Previously accepted malformed JIDs now throw `TypeError`. Parsing a complete
  address never repairs an invalid localpart through automatic escaping. The
  existing parts constructor retains XEP-0106 escaping for explicit user input.
- Equivalent Unicode/IDNA addresses compare equal; domains serialize as U-labels.
  Resource case remains significant. Stored address keys can change: migrate
  application data with collision checks, not blind replacement.
- SASL credentials retain the selected mechanism's contract; JID preparation
  does not implement SASLprep, SCRAM, account registration or server policy.
- Invalid incoming addresses cannot enter middleware or complete an IQ. Raw
  `element`/`stanza` events remain untrusted wire observations, not a validated
  identity API. Custom extension fields must explicitly use the JID boundary.
- Confusable detection, UI presentation, account provisioning, authorization and
  authenticated peer transport are separate responsibilities. Bidi validation
  does not make visually similar names safe. Do not authorize by display text.
- Lengths are checked after preparation. Network input also has XML frame/depth
  limits; standalone callers should bound the size of untrusted input before
  normalization. No server-specific truncation or arbitrary username restriction.
- Node/Bun and Chromium have executable evidence; other browser engines and
  future Unicode upgrades require revalidation. Unicode 16 is an explicit
  versioned profile, not a claim to support every future assigned character.

## Reproduction and maintenance

```sh
bun run test:all
bun tools/bench-jid.js
```

Download and unpack the official
[Unicode 16 UCD](https://www.unicode.org/Public/16.0.0/ucd/UCD.zip).
Archive SHA-256:
`c86dd81f2b14a43b0cc064aa5f89aa7241386801e35c59c7984e579832634eb2`.
The generator checks every consumed source file's digest.

```sh
bun tools/jid-unicode.js /path/to/unpacked/UCD --check
# Omit --check only when intentionally regenerating the checked-in table.
```

An optional independent oracle prints, but never rewrites, the golden digests:

```sh
python3 -m venv /tmp/xmpp-jid-oracle
/tmp/xmpp-jid-oracle/bin/pip install precis-i18n==1.1.2 unicodedata2==16.0.0 idna==3.11
/tmp/xmpp-jid-oracle/bin/python tools/jid-oracle.py
```

The oracle is not shipped or needed for normal tests. Its IDNA table has a known
exception: idna 3.11 admits U+1CCF0–U+1CCF9, whose Unicode 16 `<font>`
decompositions violate RFC 5892 §2.2. The explicit exclusion follows the source
standard, not production output. Do not refresh golden hashes automatically.

## Cost

Complete Unicode validation initially grew the Brotli bundle from 19.96 to
31.66 KiB. Packing the same properties reduces it to approximately 26.5 KiB;
the explicit budget is now 27 KiB. `bundlesize` remains a failing gate above it.
Punycode 2.3.1 remains the only added runtime dependency. No repertoire, profile
or validation rule is removed to meet the budget.

The generator stores each property independently as (gap, length) pairs, using
five-bit unsigned varints in a fixed ASCII alphabet. Each gap starts at the
previous range's exclusive end (initially zero). The decoder reconstructs ranges
once during module loading; normal validation continues to use the original
native RegExp patterns, not per-JID decoding.
Before writing, the generator checks the decoded result against every source
property for every code point. UCD checksums and independent golden hashes remain
unchanged.

Decoding adds startup work, not per-JID decompression. A shared-mask prototype
saved about one further KiB, but its palette and cross-property range merging
were rejected in favor of the simpler independent format. Literal Unicode
regexes did not reduce Brotli size. Browser startup costs must be measured
separately from Bun timings.
