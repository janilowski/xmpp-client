# XEP-0156: alternative connection discovery

Reviewed client profile, not general XRD or TLS-stack certification. Reviewed on
2026-09-17 against [XEP-0156 1.4.0](https://xmpp.org/extensions/xep-0156.html)
§§2–4 and [RFC 6415](https://datatracker.ietf.org/doc/html/rfc6415)
§§2–4.1, §5 and Appendix A for the transport audit
[#8](https://github.com/janilowski/xmpp-client/issues/8).

[RFC 6415 errata](https://www.rfc-editor.org/errata/rfc6415) checked on the
same date: 4811 (reported) proposes relative `href` support; this profile retains
XEP-0156's stricter absolute HTTPS/WSS connection URLs. 3118 (held for document
update) corrects element order in a non-normative JRD conversion example;
it does not change this client's XRD link selection.

## Profile and evidence

This is a browser-oriented WebSocket client. Discovery reads XRD, not JRD;
the additional JRD publication recommendation applies to servers. There is no
BOSH transport, TCP/SRV procedure or removed `_xmppconnect` TXT lookup.
Explicitly configured `ws://` remains application policy, not secure discovery.

The parser tests cover malformed XML, namespaces, missing/invalid addresses,
unsuccessful HTTP responses and cancellation after the decompressed byte limit.
These defensive limits are local policy, not XEP-prescribed numeric values.
The mutation runner deliberately removes ordering and template checks; assertions
must detect both defects.

## HTTPS failure and redirect evidence

[Real HTTPS scenarios](xep0156-https.test.ts) use an isolated Bun process and
disposable trusted CA, without bypassing verification. They check successful XRD
retrieval, 404/410/503 responses, stalled headers, stalled bodies and continuous
body trickles. The five-second deadline covers the entire transfer, not merely
inactivity. A separate watchdog produces an assertion result if it fails to
settle; removing the deadline must fail an assertion, not hang the runner.

The suite also checks that 301/302/303/307/308 redirects never contact their
HTTPS or plaintext HTTP targets. A mutation enabling automatic redirects is
detected. These tests establish our restrictive policy, not redirect support.

`redirect: "error"` deliberately deviates from RFC 6415 §2's SHOULD follow
redirects. The [Fetch Standard](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque-redirect)
hides headers in a manual redirect response; JavaScript cannot inspect its
`Location`. Automatic following gives no per-hop approval hook. Rejecting all
redirects prevents an HTTPS discovery request from traversing HTTP before
returning to HTTPS. The interoperability cost is explicit: redirected host-meta
deployments cannot be discovered; they must serve XRD directly or the caller
must provide a trusted WSS endpoint.

[Chromium](../browser.test.js) verifies the opaque manual response even when
`Location` is CORS-exposed, then exercises the production bundle's rejection
without contacting the HTTP target. A successful HTTPS control rules out
certificate or CORS failure as the rejection cause. This fixture's SPKI
exception is not certificate-validation evidence.

## Inherited XRD / URI review

Reviewed [XRD 1.0, OASIS Standard 2010-11-01](https://docs.oasis-open.org/xri/xrd/v1.0/xrd-1.0.html)
§§1.5–4, 7.1, with optional signature/XRDS sections 5–6 classified below;
[XML Schema dateTime](https://www.w3.org/TR/xmlschema-2/#dateTime),
[RFC 3986 §6.2.2.1](https://www.rfc-editor.org/rfc/rfc3986.html#section-6.2.2.1)
and [Web Linking §2.1.2](https://www.rfc-editor.org/rfc/rfc8288.html#section-2.1.2)
(RFC 8288 supersedes the referenced RFC 5988). The OASIS committee errata link
did not expose a separate correction set; the dated published standard is the
review baseline, not a claim that unpublished corrections cannot exist.

| Clause / condition | Processing and evidence |
| --- | --- |
| XRD §§1.5, 2.1, 7.1 | Namespace-aware XML document parser; correct root/direct-child links required. Malformed XML and hostile declarations are rejected by the shared parser. No external entities or schema fetching. |
| §2.2, optional `Expires` | The XEP suite rejects expired dates at the exact boundary, invalid calendar/UTC syntax, duplicates and child elements. It accepts future dates, leap days, `24:00:00`, XML whitespace and expanded years. Expiry uses the device clock independently of HTTP caching. The client has no additional metadata cache. |
| §§2.3–2.6, metadata | Subject/Alias/Property/Title do not redefine the authenticated discovery authority or endpoint. Tests ensure metadata and nested/foreign links cannot override direct host-wide links. Unused metadata is ignored, not consumed as a trust assertion. |
| §2.6, relation/target | Case-insensitive extension-relation comparison; canonical Web URL schemes/hosts, with path/query case preserved. Tests include mixed-case valid values. Invalid/relative URLs, credentials and unknown methods cannot become automatic connections. |
| §3.2, extensibility | Unknown extensions are ignored without changing known links; covered by foreign-namespace and nested-link cases. This is a connection-metadata consumer, not an XSD validator for unrelated properties. |
| §4, ordering | XEP-0156 §2.2 specifically overrides generic XRD order significance for these links. All permutations are tested. |
| §§5–6, optional features | No XML Signature trust or XRDS resolution. HTTPS authenticates host-meta; these optional mechanisms cannot bypass it. RFC 6415 uses a single XRD document. |

The expiry and relation regressions failed assertions before their fixes.
Mutations removing expiry enforcement or case folding must be detected, alongside
the existing ordering, template, deadline and redirect mutations.

TLS dependencies, tested runtimes and justified platform boundaries are indexed
in [the TLS audit](tls.md). The deliberate redirect deviation above remains;
passing tests do not turn it into full RFC 6415 redirect interoperability.
